# Pagination and stable ordering

Proposed D-API-02. Collections use `{items:[],page:{nextCursor:null,hasMore:false}}` inside success.data, never omit empty items or invent a zero item. Query limit integer1–100, fixture/example25;100 is a **proposed structural ceiling**, not an approved production budget/default. Runtime default/page-byte/scan/snapshot-TTL/cursor-key policies must be reviewed and configured; otherwise503 POLICY_UNAVAILABLE. Limit query with cursor must equal encoded limit or400. No page numbers, OFFSET, createdAt-only Message guarantee or cross-tenant cursor reuse.

## Cursor format and authorization

Opaque base64url of canonical JSON claims followed by dot and base64url HMAC-SHA256 signature; verifier enforces finite encoded byte cap, exactly two components, canonical base64url, UTF8 JSON with no duplicate keys, strict claim schema, constant-time signature comparison, known keyId and expiry. Claims: version="1.0.0", keyId, principalId, organizationId, brandId(nullable for sole Organization), routeId, resourceId(nullable), filterHash, limit, snapshotId, lastKey, expiresAt. lastKey is route-specific, never interpolated SQL. Bind full route/method/filter/order/page size and actual authenticated principal/scope; secrets/cursor contents never analytics. Signing keys stay server-side with reviewed rotation/overlap; decoding is not authorization. Invalid signature/encoding/claims400 INVALID_CURSOR; correctly signed foreign scope404 RESOURCE_NOT_FOUND; expired/missing snapshot409 PRECONDITION_FAILED, reload first page. No arbitrary URL or executable expression in cursor.

Server creates bounded **identifier/status metadata-only** read snapshots on first page, reusing approved snapshot identity for immutable knowledge/revisions and reviewed short-lived infrastructure storage for mutable Conversation/message lists. Snapshot storage is a proposed rebuildable read cache, never another business/status authority; exact component, caps and expiry require D-API-02/D-ARCH-01/D-POL-01. Across replicas a signed cursor must resolve the same snapshot; no node-local opaque state assumption. Without reviewed snapshot mechanism mutable pagination is disabled, not silently changed to unstable lastActivityAt queries.

Every page reauthorizes and resolves current tombstones/visibility before returning rows, filling up to limit from the frozen IDs as allowed by bounded scan policy. Deletion/removal skips inaccessible IDs; never returns cached deleted content. Missing unrelated IDs don't reveal deletion count. Snapshot absence returns409. New inserts/updated sort keys do not move rows inside an existing snapshot; refresh starts new snapshot. No promise deleted rows can be reconstructed. Terminal-attempt current status overlays on message reads may change, but acceptance order/identity stays frozen; prior eligibility for AI history remains the **separate frozen ADR-016 receipt**, never this UI read snapshot.
