# Trustworthy, Versioned Brand Brain Knowledge

Effective design: 2026-10-13. Status: planned product and persistence design, not implemented. Authority: [MVP_SCOPE.md](MVP_SCOPE.md); retention and erasure: [DATA_LIFECYCLE.md](DATA_LIFECYCLE.md). This document supersedes entity-level `source: both` as evidence of a field’s origin and the previous completeness-on-read-only decision.

## Product contract and source of truth

Each material business field has inspectable origin, evidence, approval and verification history. This includes Organization profile, Brand identity/goals, BrandVoice, Products/Services, Audiences and optional Competitors. Infrastructure fields (IDs, timestamps, job states) are not business facts. Scalars are tracked individually; an atomic list such as toneAttributes or keyFeatures is one field unless individual items have different origins, in which case item provenance must accompany that list. `both` in old field eligibility tables meant manual or imported was allowed; it is not an origin value.

The immutable APPROVED_KNOWLEDGE Artifact payload is the canonical approved full Brand Brain snapshot. BrandBrainRevision supplies one-to-one approval metadata, ordering, links to prior/restored revisions, and its calculated completeness snapshot; it does not duplicate business values. Brand.currentRevisionId is the sole active-version selector. Organization/Brand/BrandVoice/Product/Service/Audience/Competitor tables and KnowledgeIndex are transactionally maintained **projections** of that selected snapshot, not independent editable sources of truth. Historical snapshots preserve values even if a repeatable record is removed from current projections. Pending/rejected proposals remain KNOWLEDGE_CANDIDATE artifacts and never become current knowledge.

There is no new fact-value table, alternate version store, or independently updated score column. Business writes must go through Knowledge Management’s approval transaction. Initial signup may create a draft Organization/Brand projection skeleton; it is not trusted knowledge until the Owner explicitly saves an approved snapshot. Readiness and Context Engine use currentRevisionId, never an unapproved skeleton.

## Field and proposal contracts

A versioned payload contract contains `brandId`, `ontologyVersion`, `members` (active entity IDs/types), and a `facts` array with unique `(entityType, entityId, fieldPath)` keys. Paths are canonical ontology attributes; list item identities are stable when per-item provenance is needed. Values preserve their declared JSON type, not serialized strings. Whole-record membership and explicit removed keys are preserved in historical snapshots. Missing mandatory facts have no approved value; a reviewed clear/removal is recorded in the new snapshot’s change metadata and previous value remains in history.

| Field metadata              | Required semantics                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `origin`                    | MANUAL, IMPORTED or DERIVED. No BOTH. Manual edits that change imported text become MANUAL and retain the original evidence as supporting lineage. Pure confirmation leaves origin IMPORTED.                                                                                                                                                                                                   |
| `evidence`                  | Imported facts require sourceArtifactId and sourceDocumentId; sourceLocation if available (page/heading/section/chunk/character range/URL fragment). Record locationUnavailableReason if absent. Multiple evidence entries allowed; one submitted source per import job remains MVP.                                                                                                           |
| `derivation`                | DERIVED requires rule/model+version and exact input `(revisionId, entityType, entityId, fieldPath)` references, or source evidence for an extraction-based inference. Distinguish copied source text from inferred business claims. Derived claims on otherwise import-eligible fields require a supported derivation rule and Owner approval; automatic knowledge inference remains deferred. |
| `approvalStatus`            | Approved snapshots contain APPROVED facts only. Candidate payloads use PENDING_REVIEW or REJECTED with actor/time/reason in decision metadata; eligibility is not approval. Removed facts are historical, not current approved nulls.                                                                                                                                                          |
| `valueRevisionId`           | Revision that introduced this exact approved value/provenance; resolve approver and approval time through its BrandBrainRevision. Unchanged fields retain the prior ID.                                                                                                                                                                                                                        |
| `supersedesValueRevisionId` | Prior introducing revision for this same fact key, if replaced; null for first value. Resolve the old value using this revision + the same key. Never mutate the old revision’s facts.                                                                                                                                                                                                         |
| `verifiedInRevisionId`      | Revision recording the latest explicit Owner verification of this field/evidence. Resolve lastVerifiedAt and verifier from that revision’s approvedAt/approvedBy. Null is “not verified”; creation/import time is not verification.                                                                                                                                                            |
| `verificationDueAt`         | Optional reviewed freshness deadline, not a fabricated timestamp. Default intervals, if adopted, must be versioned policy; unset means unknown, not fresh.                                                                                                                                                                                                                                     |

Every field read returns resolved `approvedByUserId`, `approvedAt`, `lastVerifiedAt`, verifier and superseded value link. These are read expansions of revision IDs, not independently writable copies in payloads. BrandBrainRevision is canonical for revision-level ontology/approval/calculation metadata; payload ontologyVersion is a validated manifest copy that must agree, never a separately editable setting. Approving an imported proposal is explicit initial verification if the UI states that the Owner is confirming its value/evidence; restoring a value or changing another field does not silently renew its last verification. Manual author and approver may be the same Owner; originating author/time belongs in manual evidence. User FKs preserve attribution; separate legally approved account erasure must anonymize identities under the lifecycle policy rather than cascade knowledge history.

Candidate payloads identify `baseRevisionId`, canonical fact key, proposedValue, origin/evidence/derivation, eligibility/validation results, detected conflicts, and decision state. PENDING_REVIEW never has an approval timestamp. Explicit rejection records rejecting actor/time, not an approving actor. A decision audit artifact may be appended; candidate payloads are not silently rewritten after validation. Read decision state from these immutable decisions. Decision artifacts use artifactType KNOWLEDGE_CANDIDATE, producingService KNOWLEDGE_MANAGEMENT, producingStage candidate_decision and a versioned payload variant containing candidateId, action, operationId/idempotency key, request hash, actor/time and resultRevisionId if approved. Valid decision envelopes do not make rejected candidate values authoritative. Exactly one terminal decision is enforced by the candidate decision handler under lock/idempotency; same candidate cannot be approved twice.

## Approval, conflict and freshness

1. Validate origin eligibility and evidence references, types, ontology constraints, tenant ownership and entity membership. `BrandVoice.toneAttributes` remains manual-only; derived/imported attempts fail. New value imports cannot fabricate identity fields or source locations.
2. Compare proposals against the **current approved field**, using canonical field key, normalized typed value and source identity. Equal values are duplicates/evidence updates, not new truth. Different values for the same key are conflicts. Map proposed entities only through explicit IDs or unambiguous same-tenant identity matches; ambiguous matches require Owner assignment before comparison, never an automatic entity merge. Rule-based incompatible product pricing, mission/name changes, ontology/type incompatibility and deleted entity references produce review flags; semantic detection may propose flags but never resolves facts automatically.
3. Show the approved and proposed values side by side, origins, source locations, approver/approval date, last verification, confidence and reason. Owner chooses keep approved/reject proposal, approve replacement, or edit and approve. Low-confidence or conflicting eligible proposals are reviewable; schema/ontology-invalid proposals cannot be approved. Separate admin/delegated review is still Phase 2.
4. Require expectedRevisionId (including null for initial approval) and Idempotency-Key. Lock Brand and candidate decision; on mismatch return 409 with currentRevisionId and diff metadata. No last-writer-wins replacement. An edit must revalidate; reject/keep never alters current values.
5. In one transaction create a new APPROVED_KNOWLEDGE snapshot artifact and BrandBrainRevision with preallocated IDs, approvedBy/approvedAt, previousRevisionId, change reason and completeness; update projection tables/KnowledgeIndex/source pointers and Brand.currentRevisionId. Retained facts preserve their introducing/verification revision IDs. Unarchived Brand status projects readiness (ACTIVE when mandatory facts are satisfied, otherwise DRAFT); ARCHIVED is never cleared by an unrelated fact save. Publish events only after commit. Rollback leaves all projections/head/history unchanged.

Confidence, source recency and verification are independent. A higher-confidence/newer extraction never replaces an approved fact automatically. Staleness is computed from explicit verificationDueAt, unavailable/changed source, or a referenced derivation input no longer current; unknown verification is shown distinctly. Pending conflicting candidates flag review but do not invalidate the old approved value by themselves. Stale/unknown facts display warnings and can be verified individually; a verify action creates a metadata-only new approved revision with identical values and updated verifiedInRevisionId for selected fields. Evaluate due-date staleness at reads/generation and compare pinned input revisions against the current approved snapshot. Source change/unavailability is observed only from a user-triggered sequential reimport or explicit source-check outcome, using normalized source identity and captured artifact content hash/version; do not claim continuous monitoring or enable scheduled integrations in MVP. Unknown source availability remains unknown. Thresholds and defaults are unresolved Product policy, not a promise that a source proves present-day accuracy.

## Inspect and restore

Brand Brain exposes paginated revision history (number, approver/time, reason, score and changes), immutable version inspection, field history and typed diffs. The Owner can preview restoration of a prior full approved revision. Preview identifies entities to recreate/remove, changed fields, lost source access, stale evidence, ontology incompatibilities and generation-readiness consequences.

Restoration creates a **new** approved revision with previousRevisionId=current head and restoredFromRevisionId=selected historical revision. It never moves the pointer backward or erases later history. Changed/restored fields receive the new valueRevisionId, link the currently replaced introducing revision, and retain their historical origin/evidence and historical verifiedInRevisionId. Unchanged fields keep their existing IDs. Restore is explicit approval of use, not a claim of fresh verification. Recreate same logical entity UUIDs only after tenant/type/collision checks; remove current projections not in the restored membership through the same approval transaction. KnowledgeIndex must match restored active membership. Retain immutable history.

Validate old data under the **current approved ontology**, using an explicit deterministic migration mapping. Invalid/removed present field values require an edited preview; return 422 rather than invent data or restore ontology-invalid values. Restoring a valid but incomplete snapshot is permitted with explicit missing-field/readiness warnings and readyForGeneration=false. Optional correctedFacts in preview/restore are explicitly Owner-edited MANUAL values, revalidated under manual-only/type rules; omissions/removals are shown in the digest and approved diff. If source content has expired but a safe retained citation remains, show evidence unavailable and request acknowledgement; missing referential-integrity records block restoration until approved repair, never silently drop evidence links. Conversation-owned generation artifacts cannot become durable provenance references; approved source evidence/independent derivation lineage must be created before approval. Rejected/pending candidates cannot be restored as approved history.

## Persisted completeness and readiness

Each BrandBrainRevision persists `completenessScore`, `missingMandatoryFields`, `ontologyVersion`, `calculationVersion`, `calculatedAt`, `readyForGeneration` and `readinessReasons`. The calculation uses the exact approved artifact of that revision; no second score is stored on Brand. CalculatedAt is the transaction’s calculation timestamp, not the last verification time. A GET returns the head revision’s persisted result; it cannot recalculate and silently override history. A current ontology/calculation change requires explicit approved reevaluation/new revision before publication, preserving old snapshots under their original versions.

Calculation v2 and all field weights are canonical in [PRODUCT_METRICS.md](PRODUCT_METRICS.md#completeness--calculation-version-2). There are 14 mandatory slots worth 80 points: mission and manual tone worth 10 each, every other mandatory slot worth 5. Named approved Competitor and valid Primary Goal add 10 each. Offer/Audience representative selection uses highest satisfied required-field weight, ties by stable UUID, and never combines fields from different members. Save selected member IDs in artifact calculation metadata. Missing mandatory fields remain readiness blockers at any score, including ≥70; 70 points alone never authorizes generation. Approved snapshots retain historical v1 scores and dates; new approved reevaluation produces v2 rather than changing historical records.

Readiness separately requires a current approved revision, valid mandatory slots, at least one complete approved offer and Audience, valid manual tone selection, and an unarchived Brand. Missing/incompatible mandatory facts and archived Brand produce readinessReasons; unresolved/stale review flags are warnings rather than automatic replacement or scoring penalties. Runtime authorization, quotas/provider availability and Conversation deletion are request gates, not completeness. ReadinessReasons stored in a revision capture its approval-time business state; live GET/generation additionally checks current Brand archival and current ontology/calculation compatibility and returns effective readiness, reasons and snapshot revision ID without changing the historical score. Bare archival never rewrites approved history.

## Referential integrity and schema boundaries

BrandBrainRevision has actual restricted FKs to Brand, its unique approved Artifact, approving User, previousRevision and restoredFromRevision. Brand.currentRevisionId is a unique restricted FK; the service ensures it belongs to that Brand/Organization and the revision chain is acyclic. `@@unique([brandId, revisionNumber])` guarantees ordering. Type/tenant checks are mandatory because a UUID FK cannot establish them.

Product/Service/Audience/Competitor.sourceArtifactId now have actual Restrict relations to Artifact. They mean **last projection materialization artifact**, not field origin. The entity-level `source` field and RecordSource enum are removed; origin comes only from field snapshot metadata. Document.latestArtifactId and KnowledgeIndex.latestArtifactId also become explicit restricted Artifact FKs; types must be STRUCTURED_DOCUMENT and APPROVED_KNOWLEDGE respectively. KnowledgeIndex gets one row per `(brandId, describesEntityType, describesEntityId)`; it is an approved projection, not a version store.

Nested field evidence and derivation links are typed JSON references, intentionally not a second citation/value table. Their referential-integrity mechanism is explicit: Knowledge Management validates and locks every source Artifact, Document, referenced revision, user/input fact and tenant during approval/restore, checks existence and same-tenant ownership and forbids conversation-owned evidence; duplicate fact keys, dangling refs and self/future derivation cycles fail. Required imported artifact/document references remain valid identity records even when original bytes expire under an approved policy. Every retention/source/entity-erasure handler must scan approved **historical and current** artifact JSON evidence/derivation references, plus candidates, and coordinate locks with approval writers. Referenced rows cannot be physically removed without reviewed citation tombstones/redaction and versioned repair. No “best effort FK” is implied by JSON.

Before release implement the shared reference-validation/cleanup gateway, PostgreSQL JSON path lookup queries and periodic integrity scans; do not expose uncoordinated direct deletes. Existing correlation, Artifact type and tenant indexes plus Brand revision ordering support lookups; field history scans the scoped snapshots using canonical keys, with bounded pagination. Add a JSONB GIN index only after measured need (existing Artifact payload index proposal is sufficient). A conversation purge also checks revision/source evidence references, but new approved snapshots must never point at generation-owned payloads. See DATA_LIFECYCLE.md; imported/approved fact history is independently retained.

## API contracts (Owner/tenant scoped, planned)

| Method / path                                            | Request                                                                                        | Response / semantics                                                                                                                                                                 |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| GET `/brands/:id/knowledge`                              | Optional field/entity filters                                                                  | currentRevisionId; approved fields with resolved provenance/approval/verification; persisted completeness and effective readiness; review flags.                                     |
| GET `/brands/:id/revisions`                              | cursor, limit ≤100                                                                             | Immutable revision metadata; tenant scoped.                                                                                                                                          |
| GET `/brands/:id/revisions/:revisionId`                  | —                                                                                              | Full approved snapshot, approval metadata and persisted completeness; 404 for wrong Brand/tenant.                                                                                    |
| GET `/brands/:id/field-history`                          | entityType, entityId, fieldPath, cursor                                                        | Introducing/verification revisions, values, source citations and superseded links.                                                                                                   |
| GET `/brands/:id/revision-diff`                          | fromRevisionId, toRevisionId                                                                   | Typed changes/removals/member changes and provenance changes; both scoped to same Brand.                                                                                             |
| PATCH existing Brand Brain entity/voice routes           | changed fields, expectedRevisionId; Idempotency-Key                                            | Explicit manual approval through Knowledge Management; newRevisionId, completeness and effective readiness. Deletes of repeatable records also create approved membership revisions. |
| PATCH existing import candidate route                    | action confirm/edit/delete, value?, expectedRevisionId; Idempotency-Key                        | confirm/edit creates approved revision, or returns terminal rejection; decision audit retained. Never marks eligibility as authoritative approval.                                   |
| POST `/brands/:id/knowledge/verify`                      | factKeys[], expectedRevisionId; Idempotency-Key                                                | New metadata-only approved revision; selected fields explicitly verified at approvedAt.                                                                                              |
| POST `/brands/:id/revisions/:revisionId/restore-preview` | expectedRevisionId, correctedFacts?                                                            | Diff, ontology migration mapping, warnings and proposed completeness/readiness; no writes.                                                                                           |
| POST `/brands/:id/revisions/:revisionId/restore`         | expectedRevisionId, preview digest, correctedFacts?, acknowledgements, reason; Idempotency-Key | Revalidate digest of full proposed snapshot/overrides, head and ontology plus current state; create new approved revision, never pointer rollback.                                   |

409 means stale revision/idempotency-body mismatch, 422 means invalid ontology/evidence/derived inputs, 404 prevents cross-tenant existence disclosure. Initial approval uses expectedRevisionId=null. A current draft skeleton has null head, score 0 and calculatedAt=null (no persisted approved snapshot exists); response identifies this explicitly and lists missing mandatory fields. Idempotency uses an immutable decision/commit artifact with operation ID/key, request hash, actor and result revision. The handler serializes all mutations under Brand lock and searches tenant+Brand operation identity before writing; original successful response is replayed for identical retries. Same key/different request gives 409. No new mutable request-result store is required.
