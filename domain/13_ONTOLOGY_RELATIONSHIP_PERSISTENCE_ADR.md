# ADR-014 — Ontology relationships, lifecycle and reconstruction

Date: 2026-10-19. Owner: Architecture + Product. **Specified — Pending Architecture/Product Review (D-AUD-06)**. No approving identity/date, implemented graph, endpoint, database migration or launch readiness is claimed. Preserves the seven-feature MVP, canonical approved snapshots/human publication and all earlier contract bundles/ADRs. No graph database, generic graph service or new Prisma table.

## Audit and authority

Read current scope/decisions/audit/provenance/learning/security/retention, domain/Artifact/ontology/database/API, ADR-012/013, Brand Brain PRD, Extraction/KM/Context specs, Prisma and versioned Artifact/import/source-evidence contracts. The ontology1.1 narrative calls TARGETS mandatory per offer and USES ready-required without matching onboarding fields/FKs; domain lifecycles describe states absent from most tables; candidateRelationships is only a proposal. Approved snapshot2.0 contains members/facts but no explicit edge set; PROMPT_CONTEXT2.0 cannot serialize selected edges. Do not treat those gaps as implemented joins or product approval.

Three authorities:

- **STRUCTURAL:** current ownership FKs plus validated approved membership for business visibility/history. Not user-editable relationship facts; no duplicate stored edges.
- **EXPLICIT:** user-confirmed business predicates TARGETS/COMPETES_WITH. Canonical approved snapshot edges, conditionally supported by the proposed contract; no new MVP UI/route or automatic link admission. Product permission D-REL-02 is required before enabling writes/retrieval of these assertions.
- **DERIVED:** deterministic views over actual approved fact/evidence structure, with rule identity. Provenance views express recorded support, never semantic inference. USES requires a separately reviewed Product rule; no relationship is inferred merely from co-membership.

## Contract and stable identities

[Ontology-relations1.0.0](../contracts/ontology-relations/README.md) is canonical: machine registry, explicit edge/graph/commit/context-reference schemas and examples. Proposed ontology **1.2.0** makes draft/ready rules explicit; it is not an approved replacement of1.1. Existing1.1 historical validation remains version-routed. Product review is mandatory for TARGETS/USES/COMPETES semantics and cardinality even if a change is an additive ontology minor version.

Explicit relationshipId is `rel_` + SHA256(UTF8(JSON.stringify([organizationId,brandId,relationshipType,sourceEntityType,sourceEntityId,targetEntityType,targetEntityId]))), with exact uppercase enum names and lowercase canonical UUIDs. Arrays/names/revision/order/origin are not identity inputs. Validate both ID and full tuple, unique tuple/ID, no self-edge where disallowed; collision/conflicting ID quarantines rather than merges. Renaming an entity leaves identity unchanged. Removing and recreating the same business name gets a fresh entity UUID; never reconnect old edges by name. Restoring the actual retained historical entity may reuse its own UUID only after same-tenant/type/collision checks; erasure/repair policy can block restore.

An approved explicit edge stores endpoint types/IDs, tenant/Brand, MANUAL or IMPORTED origin, introducingRevisionId, lastApprovedRevisionId, supersedesApprovalRevisionId (nullable backward link), approvalDecisionArtifactId and supportingFactRefs/evidenceRefs. Ontology/registry/revision identity is inherited from its containing relationship snapshot. Resolve approver/time through the actual commit + BrandBrainRevision; do not create another approval table or writable actor copies. Future supersedingRevisionId is a **history read expansion**, never a future pointer written into immutable old data. Canonical active edge set contains only active approved assertions; absence/removal is recorded in relationshipChanges plus earlier immutable snapshots. Re-approval/reactivation of the same tuple keeps identity, preserves first introducing revision, points back to prior approval, and records a new decision. Inverse views return the same ID; inverse wire types are not stored.

Structural/derived views use deterministic scoped tuple/fact handles for reads, not explicit edges. Logical Knowledge is `(entityType,entityId,fieldPath,valueRevisionId)` under organization/Brand; it is not a new KnowledgeEntityType or fake member. Registry spellings ORIGINATES_FROM/MAY_DESCRIBE/COMPETES_WITH are wire aliases for ontology display spaces, consistent with v2 candidateRelationships.

## Approved snapshot amendment and lifecycle

v2 snapshots cannot hold approved edges or subentity dispositions, and candidateRelationships cannot record an authorized relationship decision. Propose [Artifact2.3](../contracts/artifacts/2.3.0/README.md), pending **D-REL-01** review:

- APPROVED_KNOWLEDGE/approved_snapshot adds `data.relationships` at the existing data level, preserving six existing data keys/fact schemas through exact references. It contains registry/ontology/revision manifest, full explicit edge set and typed membership dispositions; scope is inherited from the Artifact and checked against edge scope. Edge/membership changes are recorded by the sole applicable commit or existing removal/restore diff. No secondary relationship snapshot/table/head exists. Each published graph belongs to exactly one BrandBrainRevision and approved Artifact.
- KNOWLEDGE_CANDIDATE/relationship_commit records one Owner approval operation for proposed relationship-only/member-archival changes: expected/result revision, actor/time/idempotency/request hashes and changed IDs/dispositions, not another copy of approved edge values. Snapshot parent=that commit. Existing fact-only/manual/import publications retain their existing terminal commit/decision; unchanged edges carry forward. A normal entity removal atomically removes incident edges as an explicit consequence shown in its existing removal/restore preview; snapshot diff/old edges preserve that history, no duplicate approval record.
- PROMPT_CONTEXT/context adds `selectedRelationships` references for the pinned snapshot/rules, rather than smuggling edges into fake business fields or WORKING memory. Final completed2.3 context supports new refs; operational stage/error checkpoints remain unchanged2.0. PROMPT.messages can render those validated context references normally. No Gateway/source-evidence/import-control changes.

Earlier2.0/2.1/2.2/Gateway1/source-evidence1/import projection files remain unchanged. Mixed readers dispatch exact versions. No Prisma migration/new join table is needed: existing Artifact JSON + BrandBrainRevision/current head support it. Read optional edges directly from the small pinned snapshot; no independent materialized edge table for MVP. Existing business tables/KnowledgeIndex remain transactional projections. A future measured read cache/index is revision/digest-scoped, rebuildable and cannot overrule the snapshot; a physical projection table would need its own reviewed schema/constraints/migration before use.

Membership dispositions cover BrandVoice/Product/Service/Audience/Competitor: ACTIVE and ARCHIVED are retained approved members, REMOVED is a retained identity tombstone outside current members/facts. Every current repeatable/Voice member has one disposition; removed identities cannot be recycled by name. Org/Brand identity remains in members, but platform authorization and Brand.status are **live overlays**, not duplicate editable Organization/Brand states. Archive/reactivation controls for subentities are proposed D-REL-03, not new launch endpoints. Existing explicit removal can be represented now without invented status columns.

Physical removal/redaction is governed by D-POL-01; immutable history is not a legal forever-retention promise. Snapshot membership/identity allows reconstruction when current projection rows are absent. Logical removed identities and source references remain only where lawfully retained. Pure current table absence is not evidence an entity never existed or permission to infer a replacement.

## Deterministic validation, publication and restore

Validate exact supported registry/ontology version; known type and endpoint pair/direction; tenant/Brand and type ownership; selected snapshot member identity (not mutable names); disposition; unique tuple/ID; lifecycle-specific cardinalities; actual human commit/revision; allowed origin and real supporting fact/evidence refs. Reserved/unknown/reversed/dangling/cross-tenant/Brand edges reject. Draft min-zero is incomplete, not invalid; READY adds global one Brand, one active manual Voice, active offer OR Service and Audience requirements under unchanged metrics, **not** mandatory TARGETS. Required fact completeness still uses PRODUCT_METRICS, not relationship count. No model/user body can supply a trusted approval or gate override.

Explicit TARGETS/COMPETES writes and derived USES default disabled pending D-REL-02. Tests may simulate a reviewed policy without recording actual approval. Relationship-only mutation binds reviewed diff digest and expectedRevisionId/Idempotency-Key to current Owner. Compute requestHash server-side using existing stable-json-v1 canonical JSON/SHA256 over operation kind, tenant/Brand, expected revision, full reviewed resulting member/edge diff and original proposal/support refs; exclude transport timestamps/attempt IDs. The idempotency key hash is SHA256 of its exact UTF-8 value, scoped by tenant/Brand/operation, not a client assertion of approval. A changed request under the same key conflicts; a genuinely new review uses a new operation/key. Under the existing short Brand/reference lock: reauthorize, validate expected head/selected candidate/lease as applicable, replay an identical committed receipt before stale-head rejection, validate resulting full fact/membership/edge set, insert sole terminal commit + approved Artifact + BrandBrainRevision/completeness, update required relational/KnowledgeIndex projections and head, and commit. Atomic ADR-012 closure remains based on its actual per-item decisions; a relationship proposal is not a fact candidate and cannot be smuggled into review coverage. No external LLM call inside transaction, no distributed exactly-once claim. Late workers cannot approve or mutate current graph.

Relationship proposals may reference an exact original v2 candidateRelationships object digest plus original candidate Artifact; index alone is not stable identity. A fact candidate approval never approves that predicate automatically. No public relationship endpoint/extra form field is added; D-REL-02/ D-AUD-08 must approve exact review/transport binding before enabling this conditional writer.

Restore loads exact historical explicit edge set and membership dispositions from that approved snapshot, not co-membership inference, current projection links or a new model. Preview diffs current members/edges/readiness, checks ontology/mapping, current access/source availability/type/ID collisions and removals. New revision appends with previous=current/restoredFrom=history; exact endpoint tuples/relationship IDs are retained. New restore commit reapproves reinstated edges with new lastApprovedRevisionId/backward link while preserving original introduction/evidence; unchanged edges may retain prior approval refs. Legacy snapshots without recorded edges have `NOT_RECORDED` relationship availability, **not a proven empty set**. Do not silently drop currently recorded edges when restoring unknown historical graph: require reviewed preview choice to preserve explicit current edges or perform an explicitly authorized reset under D-REL-02, otherwise block. New empty graph is explicit only after a reviewed baseline; never fabricate old graph history.

Ontology-incompatible graph restore returns compatibility/repair requirement, never silently renames types, reassigns targets or broadens scope. Required projections failing cause full rollback. Optional future cache/index work uses approved atomic enqueue/outbox under D-ARCH-01 with revision/digest tags; retry/replay selects one final commit/head and cannot duplicate tuple IDs. Existing import/evidence lifecycles and gates remain intact.

## Source evidence and supporting facts

MANUAL edges need no Document/binding; explicit Owner relation decision is authority, not fabricated imported support. IMPORTED TARGETS edges require real approved supporting fact references (snapshot Artifact/revision, exact fact key/valueRevisionId) whose literal content actually supports that predicate plus real Task19 bindingArtifactId/evidenceId from the introducing fact's original candidate. Independent Product.name and Audience.segmentName in one tenant do not support TARGETS. No fake "relationship" fact/field may be manufactured. COMPETES_WITH remains manual-only for current competitor scope. Unsupported AI inference is corrected to explicit manual assertion or remains unapproved; automatic derived business learning is not enabled.

The relation commit confirms the predicate separately after actual fact/evidence review; fact approval alone is insufficient. Predicate support must retain source locator precision and immutable manifest identity, never copy offsets or ask Gateway/model for authority. Source-evidence1.0 and proposed2.2 are unchanged. Supporting facts may pin older introducing value revisions but must exist in actual approved historical snapshots; if their current value revision changes, label STALE_SUPPORT and omit affected edge from current automatic context until reviewed. Lawful source-byte loss is an availability warning under ADR-013, not a rewrite/auto-unapproval of old graph. New imported edge approval requires the existing source/support policy and authorization; missing refs/digest corruption block.

## Context retrieval and bounded traversal

Pin one approved BrandBrainRevision/Artifact, validate scope/ontology/graph, and join current authorization/Brand archival/deletion overlays. Use direct snapshot edge lookup, plus structural/provenance views from the same approved members/facts. Never read candidateRelationships as approved edges or mix row values from another revision. Global BrandVoice injection does not require claiming Product USES Voice. Include TARGETS only for task seed offers and a reviewed explicit-edge capability; no all-pairs inference. Derived USES only under exact reviewed rule/version, computed read-only.

Proposed registry default traversal: **one hop**, ≤32 selected edges and ≤32 selected endpoint nodes, sorted by task-relevant incident seed first, then registry type and relationshipId. These are reviewable contract bounds, not production SLA/approved resource budgets. Return explicit truncated flag/reason; no recursive traversal or new graph infrastructure. Fact/token/deadline bounds remain Context/Gateway policies. Counts never bypass mandatory approved grounding. D-REL-02/Engineering review and D-ARCH-01 performance evidence gate actual deployment values.

SelectedRelationships references exact source snapshot/revision, explicit edge ID or the gated USES derivation rule; structural/provenance views retain existing fact/evidence references; it is not a new business fact. Prompt Builder resolves only those approved refs. Draft/unapproved/removed/archived endpoints, stale support or unsupported rule are excluded with safe reason; archived Brand denies generation. A stale/wrong-revision/orphan cache is discarded and rebuilt from canonical snapshot or fails safely. No orphan cache triggers edge insertion or guessed entity recreation. A pinned in-flight generation may use its earlier valid revision under existing policy, but all entities/edges/context refs must agree on that one revision and live deletion/auth guards still apply.

## Deletion, history and decisions

- Audience archival (conditional D-REL-03): keep historical edge/identity, current retrieval excludes it and incident edges, readiness re-evaluates active Audience. Do not silently retarget Products.
- Product removal: explicit approved member/fact removal and incident-edge removals in one revision/transaction; history and lawful evidence remain. New same-name Product gets a new UUID and no automatic old links.
- Organization physical erasure: privileged authorized inventory/reference-aware legal/operational process, not naive schema cascades. Existing Artifact/Revision Restrict and JSON refs need coordination; lawful erasure may make historical reconstruction unavailable rather than fabricate identity. No new retention period.
- Superseded revisions remain immutable historical graphs; current head alone selects normal retrieval. Restore creates a new revision as above.
- Source Document purge/byte deletion follows ADR-013; preserve protected identity or reviewed tombstone, label lost availability. No graph cascade erases approved facts merely because source bytes expired.
- Orphan projection: discard/alert and rebuild canonical state; rename: stable entity/edge IDs; incompatible ontology/erased identity: block/repair, never infer.
