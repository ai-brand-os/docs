Started: 2026-10-20; specification/validation completed: 2026-10-21. Owner: Product + Architecture + Security. **Specified — Pending Product/Architecture/Security Review (D-AUD-01)**. Specification and executable fixtures, not runtime implementation, approval, production defaults or a new feature. Existing Workspace multi-turn behavior needs bounded prior-turn inputs; advanced memory remains excluded.

## Memory boundaries and ownership

A Approved Knowledge Memory is the one human-approved Brand Brain revision. B Conversation History is authorized stored USER/ASSISTANT messages in this Conversation only. C Working Memory is attempt-local state/context. A/B/C are specified MVP inputs. D inferred long-term conversation summaries/preferences, automatic learning, persistent generated summaries, background memory agents and cross-conversation semantic search remain excluded. B never becomes A without existing eligible explicit correction/review/publication; conversation-owned raw source artifacts cannot be silently used as imported business evidence.

Workspace Application authorizes/resources, accepts/persists current USER and ASSISTANT placeholder, allocates identities/slots, pins revision and coordinates attempts. Its in-process ConversationHistoryReader loads authorized stored rows/statuses and returns the bounded catalog under the Conversation lock. Reader depends on the repository, not Context/Orchestrator. Context receives that catalog, selects history and approved business refs. Orchestrator composes prompt and owns Message generation/final outcome; Gateway only executes its reviewed request. KM owns approved knowledge, never calls back into Workspace for automatic learning. No circular module route or separately deployed Memory Service/store.

## Ordering, acceptance and immutable cutoff

**Proposal D-HIST-01:** Conversation.nextMessageSequence BIGINT; Message.conversationSequence BIGINT; Message.replyToUserMessageId UUID for ASSISTANT, null for USER. These are minimum new order/association data; exact DDL prototype is [ordering proposal](../sql/CONVERSATION_HISTORY_ORDER_PROPOSAL.sql). **schema.prisma is unchanged.** Existing IDs/timestamps/correlation do not reliably substitute: IDs are random, timestamps can tie, nullable correlation denotes artifact chain not reply association, completion can occur later. New generation path disabled until reviewed storage/migration/readers exist.

Under proposed common lock order Brand → Conversation → retained reference rows ordered by typed UUID, with live authority rechecks, allocate USER slot n and ASSISTANT placeholder n+1, set reply FK, allocate next counter n+2; commit acceptance receipt, rows and pinned approved revision together. No LLM/tokenizer/network call or long operation inside the lock. Completion takes Brand then Conversation; deletion may take Conversation alone only if it never later acquires Brand. D-HIST-04 must reconcile this proposed order with the shared authorization/reference gateway before adoption; integration deadlock/revocation tests remain required. Counter/receipt failure rolls back; gaps from later unused reserved slots are harmless, collisions/reuse are not. Sequence denotes accepted transcript slots, not response completion chronology. JSON encodes BIGINT as canonical positive decimal strings; never convert through unsafe JavaScript Number.

History cutoff=current USER sequence−1; current USER excluded from history and serialized once at the end. At acceptance capture a bounded catalog of earlier turns/statuses/content digests under the same serialization lock as completion. A placeholder becoming COMPLETED later cannot enter an already accepted request. Cutoff alone is insufficient for mutable status: **catalog freezes eligibility/status/content identity at capture**. The acceptance receipt is the canonical attempt input manifest, not a second content store. Accepted USER/final completed ASSISTANT content is immutable; edits would require a separately reviewed version policy. Rechecking missing/changed content, revocation and deletion may deny use, never silently replace a reference or read a new revision of text.

Concurrent accepted requests serialize allocation and freeze independently: A gets n/n+1; B gets n+2/n+3. If A response was pending when B accepted, B may include A's persisted user question as unanswered but never A's subsequently completed response. No hidden wait or semantic merging. Product may prefer one in-flight operation per Conversation; that alternative is D-HIST-03, not adopted implicitly. Distinct Conversations never share counters. Duplicate idempotency key under same authenticated Owner/tenant/Conversation/operation replays original acceptance after reauthorization; changed body conflicts. Request hash binds exact current content, request kind/retry source and relevant immutable scope; stored receipt also pins the resolved revision/policy/catalog. Current head changes cannot change a replay's input. UUID alone is not receipt authorization.

Reader fetches a **reviewed finite number of recent USER turns** and their bounded attempt rows below cutoff. maxCandidateTurns/maxCandidateMessages/maxCandidateBytes are D-GW-01 policy, not defaults. If attempt fanout or aggregate candidate bytes exceed bounds, fail HISTORY_SCAN_LIMIT rather than guessing the right answer. Preflight stored content byte lengths before fetching/hashing raw bodies; oversize beyond this loader bound fails safely, whereas loaded messages within this bound but exceeding history token budget are dropped as whole turns. No unbounded transcript body read under the lock. Older unscanned prefix is explicitly recorded by scanLowerSequence/olderPrefixOmitted, not listed with raw content/IDs. Keyset pagination walks frozen receipt catalog by sequence; cursor binds request Artifact, catalog hash and next key. No live timestamp OFFSET pagination or later completion enters replay. Missing source rows/digest mismatch fail safely; lawful deletion overrides audit reproducibility.

## Eligible turns and attempt policy

Eligible USER: actual committed accepted row, status COMPLETED, same authorized Conversation, nonempty immutable content. Eligible ASSISTANT: committed COMPLETED plus nonempty final content, actual same-Conversation VALID/SUCCEEDED final RESPONSE linkage/validation; no partial stream/checkpoint qualifies. Unknown/system/tool roles reject. Wrong tenant/Brand/Conversation input is a reference violation, never silently borrowed.

DRAFT/SUBMITTING/QUEUED/PREPARING_CONTEXT/GENERATING and FAILED/CANCELLED/TIMEOUT assistants are excluded with reasons. Unsupported internal artifacts/uncommitted/purged/revoked/newer-than-cutoff records are not history. For each prior USER choose **at most one** eligible successful assistant: greatest conversationSequence among successful attempts present at capture. Later failed attempt does not convert an earlier durable successful answer to failure. Record nonselected/failed/pending attempt IDs/reasons within bounded catalog, never replay their text as an answer. USER after failed/cancelled/timeout response remains an eligible unanswered turn (review gate D-HIST-02); provider data includes no fictitious successful assistant. Stream fragments are not completed text.

Acceptance receipt replay returns same operation/Message IDs, no new USER or attempt. Gateway transport retry reuses exact prompt/attempt budget under existing policy. Explicit retry after terminal FAILED/CANCELLED/TIMEOUT creates new ASSISTANT ID/correlation/request receipt pointing to original request; **same USER, original catalog/cutoff/revision/policy/selection**, fresh authorization and remaining reviewed retry policy. Old attempt never resets. Retry is allowed only for the latest accepted USER and its latest terminal assistant attempt in this proposed linear MVP policy; an existing active attempt for that user prevents another retry. later accepted USER means old-turn branching is unsupported/conflict. Completion/regeneration of an old branch requires separate product review.

Explicit regeneration, if exposed by approved existing UX, is a new assistant generation/operation after the latest assistant attempt completed, with no active sibling, same latest USER, newly selected current approved revision and freshly captured catalog below that user's original cutoff; excludes that USER and its previous answers. No regenerated answer becomes authoritative business knowledge. This specifies a conditional transport behavior, **not a new regeneration button/API**. Product/D-AUD-08/D-REV-02 must review exact availability. Concurrent user submissions may make a terminal retry/regeneration ineligible; do not reorder accepted turns to accommodate it.

## Budgets and deterministic selection

[conversation-context1.0](../contracts/conversation-context/README.md) defines request/catalog/selection and policy schemas. No production numbers: policy includes provider/model snapshot, tokenizer identifier/version/digest, serialization/template version, review evidence, window W, maximum input I, trusted cap T, current cap U, mandatory approved-context cap K, history cap H, output reserve O, serialization allowance S and safety reserve R, plus source scan limits. Require finite nonnegative integers, positive W/I, reviewed bounds; total caps T+U+K+H+O+S+R≤W and input-side caps≤I. Gateway still independently enforces actual total/token/cost/deadline/caller/model policy.

Before selection count exact approved template/provider wire with pinned model/tokenizer. A proven reviewed upper-bound meter is allowed; unknown tokenizer/model/serialization/meter confidence blocks invocation, never chars/4 treated as exact. Test tokenizer is **synthetic UTF8-byte-per-token model**, not a production estimate. Policy resources/budgets are fixture values only. Exact whole wire count, including JSON escaping/roles/system wrappers, must fit I and W−O−R. S bounds measured serialization overhead; instruction/current/knowledge/history each fit reviewed caps. Never silently drop trusted/safety instructions, current request or mandatory approved facts.

Algorithm: resolve/revalidate request and frozen catalog; build eligible prior whole turns in user-sequence order; reserve trusted/current/mandatory business allocation; try newest turn first, extending backward while whole-turn history and exact serialized total fit. Stop at the first nonfitting recent turn: never skip it to include unrelated older turns. Selected suffix remains chronological. Drop oldest turns first when trimming a full window. An oversized most-recent prior answer may leave no history; do not partially truncate it or produce a hidden summary. User-only unanswered turn is one whole turn. Include no alternate answer just because it is shorter. Exclusion reasons distinguish failed/nonselected attempts, budget-omitted turns, older unscanned prefix and no eligible history.

If current request exceeds U or total, return safe input-too-large/ask for shorter text. If mandatory approved context exceeds K/total, fail context assembly; never remove readiness/safety or edit business facts. If no history fits, **current-turn-only fallback requires reviewed policy permission and an explicit current-only limitation disposition**. Otherwise fail HISTORY_REQUIRED. A genuine first turn with empty prior history is normal, not truncated. No automatic inference that “do that again” is self-contained: history-dependence detection is not implemented; Product must approve the disclosure/shorter-input policy under D-HIST-02/D-AUD-08. Compression/quality formulas remain disabled, no history-count/token number is factual accuracy.

## Revision pinning and prompt trust

Acceptance resolves one actual authorized compatible ready BrandBrainRevision/approved Artifact. All selected facts/relationships/context provenance and final PROMPT/RESPONSE use that one revision. Prior assistant text may have been generated against an older revision; it stays untrusted historical text with its recorded revision metadata. Current pinned approved facts take precedence for business content; old response does not become a fact ref. No rewriting old Messages or model calls to invent corrections. If a discrepancy is explicitly known, state current approved information/its source when responding; do not claim automatic exhaustive fact checking or add a claim-review UI beyond D-GTM-02.

Head changes during an in-flight accepted request do not silently repin; pinned authorized revision may finish under existing live gates. New explicit generation chooses current head. Same acceptance/terminal retry preserves original pin, provided that revision remains authorized/compatible and current live Brand/readiness/resource guards permit use. Revoked revision, archived/deleted Brand/Conversation, or failed effective readiness blocks invocation/publication; never substitute newer facts in that attempt.

Logical composition: trusted system/safety → selected approved business data → bounded prior conversation data → current USER once → typed execution metadata. This does **not** authorize new provider roles. Gateway1 task.content already accepts untrusted generation context text. Proposed registered template serializes a strict JSON data object with approvedContext, history role/content data, currentRequest and bounded executionMetadata. Provider wire uses existing SYSTEM(trusted registry instructions) and USER(that data string); historical ASSISTANT role is a data label inside USER, not a new system role. PROMPT2.0.messages records that exact wire; Gateway loads/verifies its trusted instruction/template binding and never queries Messages itself. The template's system policy defines approved-fact precedence, no tools/external actions and no execution-authority changes. Review this template/model/tokenizer binding under D-HIST-02/D-GW-01; no Gateway1 DTO alteration or arbitrary JSON reinterpretation at runtime.

Context resolves fact/history refs; Orchestrator fetches/rechecks selected immutable text, validates hashes and serializes once. Current request is not appended twice by Gateway. Private selection wireSha256 binds exact serialized existing-role final PROMPT.messages. Prompt messages and actual Gateway task bytes must agree with this hash, the reviewed template and pinned policy; a same-length text/template substitution is not valid replay. Escaped history text cannot change JSON structure, provider/policy/caller/roles or server authorization. Model obedience/injection resistance itself remains imperfect and needs adversarial real-provider testing; a malicious prior assistant/user message cannot grant tools, change tenant/provider or approve knowledge through server APIs.

Unknown old messages stay unsequenced and readable as legacy history, not automatically eligible for new generation. Update Prisma/generated client and deploy reviewed migration only after D-HIST-01/04 review; it is **not implemented by these documentation files**. Rollback disables new history writer and keeps order/manifest readers; do not drop columns, resequence old rows, strip metadata or pretend old contexts have empty history. Narrow order-column indexes support keyset reads; actual scan/locking/performance testing remains required. ## Privacy, races and failure

Reauthorize membership/tenant/Brand/Conversation and tombstones at acceptance, catalog/text fetch, immediately before Gateway egress, before each stream emission and under Conversation lock before final response+Message COMPLETED commit. Deletion serializes with acceptance/completion. If deletion wins, cancel best-effort, stop delivery and discard late results; a started external request cannot be recalled by a local tombstone. If completion wins first, later deletion still denies normal access and purges owned copies. Revoked/missing selected message reference on replay fails, never rehydrates from a deleted prompt or backup. Independent approved business knowledge remains unaffected by conversation purge.

Request/catalog/selection receipts, context/prompt/response/error/retry artifacts, queues, transient prompt buffers, content caches and provider request references are conversation-owned purge inventory. JSON references are not retention exemptions. Log only restricted content-free IDs/outcomes/version/counts under approved telemetry policy; no raw messages/prompts/selection text or cross-tenant text digests in general logs. Exact counts/digests are private audit metadata, not product metrics or new retention permission. Temporary plaintext exists only for bounded assembly/execution; clear on completion/cancel/error where feasible and apply D-POL-01/D-SEC-03 to infrastructure copies. No invented retention TTL. Active-system30day target remains proposed; backups expire separately. Provider retention/training/deletion/disclosure stays D-SEC-02; no claim remote erasure.

Provider failure/cancellation/timeout terminates only that assistant Message under existing state machine, preserving user+prior history until authorized purge. Partial SSE text never eligible. Client disconnect alone does not change status; read current attempt and stored response if complete, no duplicate generation. Duplicate final/error callbacks use expected-state transition and cannot overwrite terminal outcome or duplicate final event; no new SSE replay/reconnect guarantee. Single-response SSE unchanged, D-AUD-08 remains open.
