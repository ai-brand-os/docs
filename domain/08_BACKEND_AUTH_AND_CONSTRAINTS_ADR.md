# ADR-009 — NestJS, Prisma 7, Authentication and NULL-safe Constraints

Recorded: 2026-10-13 (documentation/design decision date, not a deployment or Founder approval date). Status: current architecture consolidation; authentication behavior and SQL are planned contracts requiring implementation/migration review. Preserves recorded NestJS/PostgreSQL framework decision and Database ADR-005’s Prisma choice. [DECISION_REGISTER.md](../DECISION_REGISTER.md) continues to govern pending product/PRD decisions.

## Backend and ORM decision

The current backend is a NestJS TypeScript modular monolith with Prisma over PostgreSQL. TypeORM is a rejected comparison, not an unresolved ORM option. Laravel is historical/superseded; its authentication tooling is not part of the NestJS design. Existing core service modules use NestJS dependency injection, not separate public microservice auth flows. This preserves TypeScript familiarity, the existing module boundaries, explicit schemas and PostgreSQL JSONB/array support.

Installed adjacent backend tooling/package declarations use Prisma 7.8.0 and NestJS 11; these are inspection evidence for tooling, not proof of an implemented provider or tested production authentication. The documentation schema adopts Prisma 7 datasource configuration: only provider=postgresql is declared in schema.prisma, the runtime connection URL is supplied by deployment prisma.config.ts, and the NestJS Prisma client uses a compatible PostgreSQL adapter. Keep CLI/client/adapter versions compatible; do not put credentials in source or a schema file. This resolves the prior P1012 schema-level-url incompatibility without a temporary schema copy. Configuration changes, code generation, migration deployment and runtime connection remain separately reviewed tasks. See [Prisma configuration reference](https://www.prisma.io/docs/orm/v7/reference/prisma-config-reference).

## Framework-compatible authentication contract — planned

Use local credential validation and signed access/refresh JWT handling in NestJS, with @nestjs/jwt and NestJS Guards (Passport integration is permitted). These are design components, not a claim that an external identity vendor, live session system, or login provider is implemented. The NestJS JWT/Guard pattern is described in [NestJS authentication documentation](https://docs.nestjs.com/security/authentication). No OAuth/SSO vendor is selected by this ADR.

- Signup validates/normalizes identity and password input, stores only an adaptive password hash (bcrypt is compatible with the inspected dependency set; cost must be benchmarked), and provisions sole Organization/Owner membership atomically. Duplicate email/concurrent signup and brute-force attempts must be handled without user enumeration. Do not emit credentials or password hashes in responses/logs.
- Login verifies credentials with bounded/rate-limited failure handling, then creates an AuthSession token family and issues a short-lived access JWT and separate-purpose refresh JWT. Access claims include sub (User ID), sid (session ID), iss/aud, iat/exp and constrained signing metadata. Refresh adds jti and a distinct purpose/audience; an access token cannot be used as a refresh token. Validate signature, allowlisted algorithm, configured issuer/audience, expiry/not-before and session ownership, never trust a token-supplied key URL or role/tenant claim.
- AuthSession stores current signed refresh-token SHA-256 hash, fixed expiresAt, rotation/revocation timestamps and User FK. Never persist raw JWTs. Proposed configurable defaults are 15-minute access lifetime and seven-day fixed session/refresh-family lifetime, pending Security/Engineering review; they are not implemented settings or onboarding targets. Rotation cannot extend the fixed family expiry silently.
- Refresh validates the refresh signature/purpose/time and session/User before atomically comparing/replacing its stored hash and issuing a new jti/token. A valid signed unexpired older token from this family that mismatches the current hash is reuse: revoke the family and require login. A random/invalid unsigned token must not revoke a legitimate session. No old-token grace overlap is assumed; browser clients serialize refresh across requests/tabs. Concrete clock skew, rotation recovery and operational limits require review/tests.
- Every protected request checks the access JWT **and** that sid exists, belongs to sub, is unrevoked and unexpired. Absent/deleted/revoked sessions fail closed. This permits immediate logout/password-change revocation without waiting for access-token expiry. Revoke current family on logout; security/account-wide revocation covers all User sessions. Cache strategy must not defeat immediate revocation; default design uses authoritative checks. SSE uses authenticated fetch/Authorization headers, never access tokens in URL queries; stream publication rechecks revocation and deletion.
- Browser access JWT stays in memory and is sent in Authorization: Bearer; never persistent browser local storage or URL parameters. Refresh JWT is a Secure, HttpOnly, host-only __Host- cookie with Path=/ and SameSite=Lax, read only by auth refresh/logout flows. Business APIs never authenticate from a refresh cookie. Auth cookie mutations require Origin/CSRF validation; SameSite alone is insufficient. Apply an explicit credentialed CORS allowlist, TLS and secret/key rotation. Fail startup/request handling closed when required issuer/audience/key/database/session configuration is absent; never substitute development secrets in production. Native clients need equivalent protected credential storage under a separate client contract.
- Auth endpoints: POST /auth/signup and /auth/login issue access JSON and Set-Cookie refresh credential; POST /auth/refresh rotates both credentials; POST /auth/logout revokes current session and expires its cookie. Invalid credentials/session produce 401; ownership-sensitive object lookups return non-disclosing 404. Token/CSRF/refresh hashes, credentials and signed cookies are never included in telemetry or source artifacts.

Organization authorization is distinct from authentication: NestJS Guards resolve current database membership/role and the resource’s actual Organization/Brand for every direct or nested operation. MVP allows the sole Owner’s one Organization/Brand only; enum/membership capacity does not authorize team/Agency access. Do not authorize based only on organizationId in a route, token or request body. Validate tenant ownership of Conversations, Messages, artifacts, historical revisions and source references; check deletedAt/readiness where applicable. Internal purge workers use narrowly scoped service identities, not reusable user refresh tokens. Core service calls receive validated tenant/principal context from the application boundary; they cannot infer permission from possession of an artifact UUID.

AuthSession is planned platform security state, **not** the rejected WorkspaceSession aggregate. User→AuthSession physical cascade only removes that user’s login state; authoritative session-absence checks reject residual tokens. It cannot bypass Conversation/knowledge Restrict relationships or perform business-data erasure. Auth-session retention, email verification/reset delivery, signing keys, hash cost, issuer/audience, CSRF secret and exact TTL/rate/skew policies require implementation/security review; no email sender or identity vendor is invented here.

## SQL decision and NULL audit

Canonical migration supplement: [sql/MVP_CONSTRAINTS.sql](../sql/MVP_CONSTRAINTS.sql). It is designed to run within a reviewed transaction after Prisma-generated DDL; it is not a deployed migration. [PostgreSQL array functions](https://www.postgresql.org/docs/15/functions-array.html) specify cardinality(empty)=0 while array_length on an empty dimension yields NULL. PostgreSQL CHECK accepts a NULL result, so both whole-column NULL and an empty array must be addressed explicitly. See [PostgreSQL CHECK/NOT NULL constraints](https://www.postgresql.org/docs/15/ddl-constraints.html).

```sql
ALTER TABLE brand_voices ALTER COLUMN tone_attributes SET NOT NULL;
ALTER TABLE brand_voices DROP CONSTRAINT IF EXISTS tone_attributes_cardinality;
ALTER TABLE brand_voices ADD CONSTRAINT tone_attributes_cardinality
  CHECK (tone_attributes IS NOT NULL AND cardinality(tone_attributes) BETWEEN 2 AND 4);
```

Prisma 7’s generated DDL was inspected: ToneAttribute[] and all required String[] columns are nullable at the PostgreSQL level even without a Prisma ? marker; @default([]) does not enforce NOT NULL. The supplement explicitly sets all ten list columns NOT NULL and rejects NULL elements/multidimensional shapes. Tone count rejects zero/one/five and accepts two/four. Allowed enum values come from PostgreSQL’s enum; duplicate tones/manual-only provenance and field readiness remain service validations. A missing tone during draft setup means no BrandVoice row until a valid manually approved list exists; never invent tones or relax the minimum to insert an empty draft voice.

| Constraint / field | NULL treatment and Prisma consistency |
| --- | --- |
| Tone cardinality and list shape | Column NOT NULL + explicit non-NULL cardinality check; CASE shape guard safely rejects multidimensional/null-element lists. Empty=0 fails minimum. |
| Other nine required scalar lists | Explicit NOT NULL; empty arrays allowed; reject multidimensional or NULL-element lists. Readiness still validates approved nonempty required business fields. |
| Revision number/score/time | Required Int/DateTime generated as NOT NULL, plus strict checks for positive number, 0–100 and calculatedAt≥approvedAt. NULL cannot bypass comparison. |
| previousRevisionId/restoredFromRevisionId | Intentionally optional restricted FKs; explicit IS NULL OR not-self permits no previous/restored source, rejects self links. Same-Brand/acyclic ancestry remains service-checked. |
| readyForGeneration snapshot | Required Boolean; true additionally requires non-NULL empty missing-fields/reasons lists. This is necessary consistency, not a complete database proof of approval/readiness. |
| mission/vision ≤300 characters | Mission required column; draft empty string intentionally possible but not an approved fact. Vision explicitly permits NULL; non-NULL length checked. |
| KnowledgeIndex confidence | Required integer, explicit 0–100 guard; no NULL bypass. |
| Purge attempts/target/status metadata | Required count≥0 and target≥requested; COMPLETED needs completedAt, EXCEPTION needs nonempty reference+reviewAt. Do not hardcode the still-proposed 30-day legal policy as a SQL equality. |
| Auth hash/expiry/rotation/revocation | Required hash/expiry with safe hash shape and expiry>createdAt; optional rotation/revocation NULL means not yet rotated/revoked, non-NULL must be ≥creation. |
| Optional artifact/head/record pointers and Brand uniqueness | NULL head/source pointers permit draft/no-source state, never approved readiness. UUID FKs enforce existence only; service enforces same tenant/type. Brand.organizationId required unique enforces at most one Brand, not completed onboarding. |
| Artifact payload index | Prisma declares the PostgreSQL GIN JsonbPathOps index; remove duplicate raw-index instructions. It is an index, not validation of JSON fact references. |

CHECK cannot prove cross-row approval, source/tenant equality, JSON evidence integrity, distinct tones, single-Owner account entitlement, verified external purge or a legal hold’s validity. Preserve the explicit transactional service mechanisms in KNOWLEDGE_PROVENANCE.md/DATA_LIFECYCLE.md. Existing nullable lists/invalid rows must be inventoried and reapproved/repaired before NOT NULL/check installation; the script deliberately fails rather than silently coalescing invalid data. Schema changes such as making a required scalar nullable require a simultaneous constraint review.

## Rollout and validation

Keep sql/MVP_CONSTRAINTS.sql in the reviewed deployment migration transaction; Prisma cannot express these CHECKs in schema.prisma. Inspect generated migration SQL, validate existing data, apply constraint/NOT NULL changes, and validate generated client compatibility before deployment. The docs repository does not apply a migration to the adjacent backend or any active application database. Test only a private temporary PostgreSQL cluster/schema and roll back test objects.
